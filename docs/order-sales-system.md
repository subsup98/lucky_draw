# 예약 구매 / 일반 판매 주문 시스템 진행 기준

이 문서는 2026-06-24에 정리된 신규 요구사항을 개발 진행 기준으로 보강한 문서입니다.

## 1. 서비스 목표

상품을 판매하는 온라인 주문 시스템을 만든다. 판매 방식은 **예약 구매**와 **일반 판매**로 나뉘며, 관리자는 주문자 정보, 결제 상태, 발송 여부, 현장 수령 여부, 송장, 배송 상태, 매출 통계를 관리한다.

## 2. 핵심 판매 방식

### 예약 구매

- 입고 전 주문을 먼저 받는다.
- 입고 후 순차 발송한다.
- 순차 발송 기준은 결제 완료 순으로 한다.
- 부분 입고 시 입고 수량 안에 들어오는 결제 완료 순번의 주문 항목을 `READY_TO_FULFILL` 대상으로 선정한다.
- 한 주문 항목 수량이 남은 입고 수량보다 크면 해당 주문 항목부터 다음 차수 대기로 둔다.
- 택배 수령과 현장 수령을 모두 지원한다.
- 현장 수령은 수령 완료 여부를 별도로 관리한다.

### 일반 판매

- 재고가 있는 상품을 즉시 판매한다.
- 결제 완료 후 당일 발송을 목표로 한다.
- 당일 발송 대상은 **당일 15:00까지 결제 완료된 주문**으로 한다.
- 송장 입력과 배송 상태를 관리자 페이지에서 관리한다.
- 송장 미입력은 결제 완료 후 발송 준비 상태가 **1일 초과** 지속된 주문을 관리자 이슈로 본다.

## 3. 권장 DB 구조

| 테이블 | 목적 |
|---|---|
| `users` | 사용자 기본 정보 |
| `products` | 상품 정보, 예약/일반 판매 구분 |
| `orders` | 주문 전체 정보 |
| `order_items` | 주문에 포함된 상품과 주문 당시 가격/상품명 스냅샷 |
| `payments` | 결제 시도, 입금 확인, 환불 기록 |
| `shipments` | 택배 배송지 스냅샷, 택배사, 송장, 배송 상태 |
| `pickups` | 현장 수령 상태, 수령 장소, 확인 관리자 |
| `notifications` | 사용자/관리자 알림 발송 내역 |
| `admin_users` | 관리자 계정과 권한 |
| `privacy_access_logs` | 개인정보 조회/수정/다운로드 감사 로그 |

## 4. 상태 분리 원칙

| 상태 구분 | 관리 위치 | 예시 |
|---|---|---|
| 주문 상태 | `orders.order_status` | 주문 접수, 결제 대기, 처리 중, 완료, 취소, 환불 |
| 결제 상태 | `payments.payment_status` | 결제 대기, 입금 확인 필요, 결제 완료, 실패, 환불 완료 |
| 배송 상태 | `shipments.shipping_status` | 배송 전, 발송 준비, 송장 입력 완료, 배송 중, 배송 완료, 배송 보류 |
| 현장 수령 상태 | `pickups.pickup_status` | 현장 수령 대기, 수령 완료, 수령 취소 |

## 5. 예약 구매 상태 흐름

```text
주문 접수
→ 결제 대기
→ 결제 완료
→ 예약 확정
→ 입고 대기
→ 발송 준비 또는 현장 수령 대기
→ 송장 입력 완료
→ 배송 중
→ 배송 완료
```

현장 수령은 다음 흐름을 따른다.

```text
주문 접수
→ 결제 대기
→ 결제 완료
→ 예약 확정
→ 입고 대기
→ 현장 수령 대기
→ 현장 수령 완료
```

## 6. 일반 판매 상태 흐름

```text
주문 접수
→ 결제 대기
→ 결제 완료
→ 발송 준비
→ 송장 입력 완료
→ 배송 중
→ 배송 완료
```

MVP에서는 관리자가 송장을 입력하면 배송 상태를 `배송 중`으로 자동 변경해도 된다. 고도화 단계에서는 `송장 입력 완료`와 `배송 중`을 분리한다.

## 7. 관리자 핵심 화면

- 주문자 목록
- 상품별 구매자 상황 시트
- 예약 구매 순번/입고 후 발송 관리
- 무통장 입금 확인
- 송장 입력
- 배송 상태 관리
- 현장 수령 상태 관리
- 매출 통계: 일간, 주간, 월간, 연간, 달력 기준
- 알림 관리

## 8. 오픈 결정 사항

- 현장 수령에도 주소 입력을 필수로 받을지 여부
- 무통장 입금 대기/자동 취소 기준: 5분 또는 10분 등 운영 가능 시간 논의 필요
- 카카오톡 채널/SMS 발송: 운영자가 카카오톡 채널을 만든 뒤 외부 발송 연동 진행
- 택배사 API 연동 시점
- 재고 차감 시점: 주문 접수 vs 결제 완료
- 배송 지연 판단 기준: 택배사 인계 후 며칠 기준으로 지연 알림을 띄울지 논의 필요
- 관리자 담당자 라우팅: 초기 담당자는 1명으로 운영하되 특정 인물 지정 필요
